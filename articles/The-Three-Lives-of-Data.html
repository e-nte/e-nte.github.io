Introduction: One File, Three Threat Models

A single file can be perfectly protected at one moment and completely exposed the next—without anything about the file itself changing. What changes is where it is and what is happening to it.

Most security conversations blur this distinction. "We encrypt our data" is offered as a complete answer, when in fact encryption is a family of controls, each designed for a specific condition. A control that is excellent in one state can be irrelevant in another. Full-disk encryption is close to useless against an attacker who has already logged into the running machine. Transport encryption is close to useless once the data has arrived and been decrypted for processing. And a hardware enclave does nothing for a backup tape sitting in a warehouse.

The way to organize this is by data state, a framing that appears across standards and guidance, including the NIST Cybersecurity Framework, which addresses data at rest, in transit, and in use as separate protection categories. This article walks through those three states in order, and adds a distinction that most treatments skip: transit happens twice. Data crosses networks between systems, and then it crosses memory inside a system. These are different journeys with different controls, and the gap between them is where many assumptions quietly break.

The one-line version: "We encrypt our data" is not a security posture. It is a category of controls, each designed for a specific state.

This is a foundational piece. It does not assume familiarity with zero trust architecture, policy engines, or mutual authentication. It asks a simpler question: for this data, right now, what is the actual threat—and what actually reduces it?

1. Data at Rest

What "at rest" actually covers

Data at rest is data stored on a medium and not currently moving or being processed: files on disk, rows in a database, objects in cloud storage, blocks on a backup volume, records in an archive. The defining characteristic is that the data is persistent—it survives the process that created it.

The characteristic threat follows from that persistence. An attacker who obtains the storage medium, or a copy of it, has time. They are not racing a live session. They can analyze, brute-force, or exfiltrate offline, at their own pace, without triggering authentication events on the original system.

Three layers of at-rest encryption

"Encrypted at rest" is not one control. It is at least three, and they protect against different things.

Full-disk or volume encryption (FDE) encrypts the entire storage device beneath the filesystem. It is transparent to applications and requires no code changes. Its real value is narrow but important: it protects data on lost, stolen, or improperly decommissioned hardware, and it supports compliance requirements around physical media. It offers no protection once the operating system is running and the volume is unlocked—at that point, the data is simply readable by anything with filesystem access.

Database-level encryption, such as Transparent Data Encryption, encrypts the database files and logs beneath the query engine. It protects against theft of the database files themselves. It typically does not protect against a compromised database account, because the database decrypts on behalf of whoever queries it.

Application-level encryption happens before data is handed to storage at all. The application encrypts fields or records, and the storage layer only ever sees ciphertext. This is the strongest of the three because the trust boundary shrinks: a compromised database administrator cannot read what the application never stored in readable form. The cost is real—you lose the ability to search, sort, or index on encrypted fields without additional design work.

The practical takeaway: these layers stack, and the choice between them is a decision about who you are willing to trust with plaintext.

The key-management dependency

Every encryption scheme above reduces to a key. If the key sits in the same place as the ciphertext, or in a configuration file readable by the same compromised process, the encryption is decorative.

This is why at-rest protection is inseparable from key management: hardware security modules, cloud key management services, envelope encryption where a data key is itself encrypted by a longer-lived key-encryption key, and rotation policies that limit how long any single key is exposed. NIST SP 800-57 is the reference standard here, and the principle it enforces is simple—the key must live somewhere the ciphertext does not.

Where at-rest protection fails in practice

Three failure modes dominate:

  • Misconfiguration — publicly readable storage buckets and unauthenticated backup endpoints remain a leading cause of exposure. The encryption was fine; the access control was not.
  • Key sprawl — keys embedded in code, committed to repositories, or shared across environments.
  • Backups treated as second-class — production systems are hardened; backup copies are often not, and they contain the same data.

2. Data in Transit

Transit has two legs, not one. Data crosses the network between systems, and then it crosses memory inside a system. Most treatments collapse these into a single state. They should not, because the controls are different and the gap between them is where the assumptions break.

2a. Network Transit

Network transit is data crossing a channel between two systems: a browser and a web server, a service and a database, an application and a third-party API, a data center and a cloud region.

The standard controls. Transport Layer Security (TLS) is the baseline, and modern deployment means TLS 1.3 with forward secrecy, enforced rather than optional. IPsec protects traffic at the network layer for site-to-site and remote-access links. VPNs tunnel traffic across untrusted networks. For service-to-service traffic, mutual TLS (mTLS) adds client authentication, so both ends prove identity rather than only the server.

Two details matter more than they appear. First, forward secrecy means a compromised long-term key cannot retroactively decrypt previously captured sessions. Second, certificate validation must actually be enforced—a surprising amount of internal traffic runs encrypted but with validation disabled, which preserves confidentiality against a passive observer while offering nothing against an active interceptor.

The threat model. Three categories:

  • Passive interception — reading traffic off the wire or out of the air.
  • Active interception — man-in-the-middle, where an attacker positions themselves between endpoints and impersonates one side. This is what certificate validation and mTLS defend against.
  • Harvest now, decrypt later — an adversary captures encrypted traffic today and stores it, intending to decrypt it once a cryptographically relevant quantum computer, or simply a leaked key, becomes available. Forward secrecy limits the damage; post-quantum key exchange is the longer-term answer, and migration planning for it is already underway in serious organizations.

2b. Memory Transit: the overlooked middle

Here is the gap. Network encryption terminates at the machine boundary. When a packet arrives, TLS is decrypted by the kernel or the application, and from that instant forward the data is traveling in a completely different channel: across the memory bus, through CPU caches, into process heap, into buffers.

This is transit. The data is in motion. It is just not covered by any of the controls above, because those controls were designed for a threat model that assumes the host is trustworthy.

The overlooked transition: Network encryption ends at the machine boundary. What happens next is a different transit regime with different controls.

Memory transit is where several assumptions break:

  • Encryption does not follow the data inside the machine. TLS protected the wire; nothing protects the buffer.
  • The boundary between "in transit" and "in use" is not a clean line. Decryption happens somewhere, and that somewhere is a moment of exposure—the plaintext exists, even if only briefly.
  • Compromise of the host converts transit into an extraction opportunity. A process with sufficient privileges can read another process's memory, and crash dumps, core files, and swap partitions can carry plaintext to disk.

Treating memory transit as its own concern is what makes the transition to the third state coherent. The data does not jump from the network directly into safe processing. It passes through an unprotected corridor first.

3. Data in Use

The plaintext problem

Data in use is data being actively read, computed on, transformed, or served—data resident in memory or in a CPU register while a process works with it.

The defining difficulty is unavoidable: to process data, software must be able to read it. Encryption protects data from everyone except the party that holds the key. During processing, the application is that party. So the data is decrypted, and for the duration of the computation, it exists in plaintext.

This means the protections described in the previous two sections simply do not apply here. Encryption at rest protected the storage medium. Encryption in transit protected the wire. Neither protects a value sitting in a heap allocation while a function operates on it.

The attack surface of the processing state

Because plaintext must exist, the processing state has the richest attack surface of the three:

  • Memory scraping and process dumps. Malware, a compromised dependency, or a privileged insider reading process memory directly—including keys, session tokens, and credentials as well as the data itself.
  • Cold-boot and physical attacks. Memory contents can persist briefly after power loss and be recovered.
  • Side-channel leakage. Timing, cache access patterns, and power consumption can reveal information about data being processed without reading it directly.
  • Vulnerabilities in the processing code itself. A memory-safety bug, a deserialization flaw, or a previously unknown vulnerability can hand an attacker the data or the keys. This is the case where no amount of encryption around the computation helps, because the attacker is inside the computation.
  • Privileged access at the platform level. A cloud provider operator, a hypervisor administrator, or anyone with host-level access sits beneath all application controls.

Foundational controls

Four families of controls address this state, at increasing levels of maturity.

Confidential computing and Trusted Execution Environments (TEEs). A TEE is a hardware-isolated region of memory and execution—examples include Intel SGX, AMD SEV-SNP, and Arm Confidential Compute Architecture. Data inside the enclave is encrypted in memory and inaccessible to the host operating system, the hypervisor, and the cloud operator. Critically, remote attestation provides cryptographic evidence that the workload is running in a genuine, untampered enclave before sensitive data is released into it. This is the most direct answer to the data-in-use problem, and it is the reason hardware-enabled security is now a distinct topic in standards work such as the NIST IR 8320 series.

Memory and cache protection. Full memory encryption, cache isolation, and protections against speculative-execution leakage reduce the window in which plaintext is readable even outside an enclave.

Runtime policy enforcement. Controls that watch process behavior—unexpected system calls, unusual memory access, anomalous outbound connections—and block rather than merely alert. Because they act during execution, they can respond to behavior that no signature anticipated.

Not decrypting at all. The cheapest control is often to shrink the plaintext surface. Tokenization replaces sensitive values with meaningless substitutes resolved elsewhere. Data masking substitutes realistic but fake values. Data minimization means the processing step simply does not load fields it does not need. Further along the curve, homomorphic encryption allows computation on ciphertext without decryption, and secure multi-party computation lets parties compute jointly without revealing inputs—both promising, both currently limited to narrower workloads and higher cost than mainstream processing.

What this does and does not solve

Confidential computing substantially raises the bar against infrastructure-level attackers and privileged insiders. It does not protect against a vulnerability inside the attested enclave—if the code running there is flawed, the isolation is intact and the data still leaks. It also introduces operational complexity around attestation, key release policy, and performance, and its guarantees are only as strong as the vendor's hardware implementation.

The honest framing: data in use is the hardest of the three states, and the controls here reduce risk rather than eliminate it.

Summary: State-Aware Security

The three states are not a taxonomy for its own sake. They are a diagnostic tool. When someone claims "the data is encrypted," the useful follow-up questions are always the same:

  • At rest — encrypted at which layer, with keys held where, and are the backups covered too?
  • In network transit — validated TLS with forward secrecy, and is internal traffic included?
  • In memory transit — who can read this process's memory, and does plaintext reach disk through swap or dumps?
  • In use — how much plaintext has to exist, for how long, and what isolates the environment that holds it?

"Encrypt everything" is not a strategy. Knowing which state you are protecting, from whom, and with what key is. The controls stack, the threat models differ, and the weakest state determines the actual exposure—which is usually the one nobody wrote a policy for.
